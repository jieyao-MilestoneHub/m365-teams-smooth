⑤ Data model & retention

The audit is the permanent source of truth; everything else is working storage or a rebuildable read model.

What this view shows

Three storage zones with different lifecycles. The append-only audit is permanent — retention never touches it. Checkpoints and the idempotency ledger are working storage that can be reclaimed after a retention window once a trial concludes. The approval queue and the precedent memory are read models: derived, indexed, and always rebuildable from the events and the audit.

permanent (source of truth) working storage (purgeable) read models / indexes

Design rationale

  • Separate the ledger from the scaffolding. A trial needs checkpoints while it runs and an audit record forever. Splitting the two means retention can reclaim space indefinitely without ever weakening the record of what was decided and done.
  • Idempotency as data, not memory. A verdict claims a row in a ledger keyed by trial and verdict; a replay finds the claim and returns the recorded outcome. No process state is involved, so the guarantee survives restarts and horizontal scale.
  • Read models are derived, never authoritative. The pending-approval queue is an index over append-only events. It can be dropped and rebuilt at any time; it can never disagree with history, because history is the events.
  • Precedent memory favors explainability over recall. Each closed trial leaves a compact, human-readable summary, retrieved by subject and tag overlap and cited in the agentic prompts. The retrieval method sits behind a port, so semantic search can replace it without touching the pipeline.
  • The backend is a connection string. SQLite for local runs, Postgres when deployed — same schema, same guarantees, no redesign.

Key guarantees

  • Audit rows are append-only and excluded from every purge path.
  • Losing all working storage after a trial concludes loses no truth — the audit holds the complete record.
  • A repeated verdict resolves through the ledger; double execution is structurally impossible.
  • Queues and precedents can always be rebuilt from the events and the audit.
