③ Approval sequence & separation of duties

A requester can propose but never approve their own change — and a repeated verdict can never execute twice.

What this view shows

The time-ordered approval flow, top to bottom: a requester submits a change and sends it for approval; an approver — resolved from a configured directory, never the requester — pulls the pending queue and decides; only then does the court resume from its checkpoint and execute. The red box is the separation-of-duties gate, the green box the idempotent gate.

Design rationale

  • Enforced in the service layer, not the UI. The same gates run identically whether the decision arrives from a card button, an MCP tool, or any future surface. There is no privileged path around the check, because there is only one path.
  • Quorum is derived, not hand-picked. The impact evidence tags determine which roles must approve; the roles resolve to identities through a configured approver directory. Changing who approves what is a configuration change, not a code change.
  • Low-risk changes scale down. When policy scores a change low and no approver role fires, the requester's own confirmation at the review gate is the execution authority — governance proportional to risk, with the same audit either way.
  • Asynchronous by construction. Submitting returns immediately; the decision may come hours later from a different process. Resume happens from the checkpoint, so no server has to stay alive — or stay the same server — across the gap.
  • The queue is an index, not the truth. Approval actions land as append-only events; the pending queue is a rebuildable read model over the open items.

Key guarantees

  • A requester can never approve their own change; an empty or unproven identity is rejected.
  • The same verdict cast twice — from any surface — returns the recorded outcome and cannot double-execute.
  • Every outcome (approve, reject, withdraw, revision request) is recorded in the append-only audit with the decider's identity and note.
  • Execution starts only after quorum is satisfied, and honors the run mode (dry-run predicts, live applies).
